Fork, branche personnelle et pull request (devoir pratique)

1h
1

Énoncé au propre

Dans le cadre de votre parcours, vous avez été initiés à Git. Dans ce devoir, vous devez prouver vos connaissances. Il vous est demandé de :

  1. Faire un fork du dépôt : https://github.com/alexgnac/devoir_L2IRT_ESGIS.git
  2. Répondre au QCM Test_Git disponible dans le dépôt en cochant directement dans le fichier PDF.
  3. Créer une branche nommée sous la forme « nom-prénom-G-numéro ». Exemple : agossou-jean-G-3 pour l’étudiant Agossou Jean du groupe 3.
  4. Enregistrer puis valider les modifications dans cette branche et faire un pull request.

NB : aucun pull request ni commit ne sera accepté après l’heure.

Corrigé détaillé

Essaie d’abord seul, puis ouvre chaque partie pour comparer.

Fork, clone, pull request : qui fait quoi ?
  • Fork (sur GitHub) : copie du dépôt dans ton compte GitHub. Tu n’as pas le droit d’écrire sur le dépôt du prof, mais tu as tous les droits sur ton fork.
  • Clone (sur ton PC) : copie de ton fork sur ton ordinateur.
  • Pull request (sur GitHub) : demande au prof d’intégrer ta branche dans son dépôt.
Étape 1 — faire le fork
  1. Ouvre https://github.com/alexgnac/devoir_L2IRT_ESGIS connecté à ton compte GitHub.
  2. Clique sur Fork (en haut à droite), garde le nom proposé, valide Create fork.
  3. Tu es maintenant sur https://github.com/TON-COMPTE/devoir_L2IRT_ESGIS.
Étape 2 — cloner ton fork et créer ta branche

Remplace par ton nom, prénom et groupe, en minuscules et avec des tirets (pas d’espace ni d’accent dans un nom de branche).

Étape 3 — remplir le QCM et l’enregistrer dans Git

Ouvre Test_Git.pdf, coche tes réponses, enregistre le PDF (même nom, même dossier). Puis :

Piège classique

Si tu oublies de sauvegarder le PDF avant git add, Git ne voit aucune modification. git status doit afficher modified: Test_Git.pdf avant le commit.

Étape 4 — ouvrir le pull request
  1. Sur ton fork, GitHub affiche un bandeau « agossou-jean-G-3 had recent pushes » : clique Compare & pull request.
  2. Vérifie la cible : base repository = alexgnac/devoir_L2IRT_ESGIS, branche main (ou master) ; head = ton fork, ta branche.
  3. Titre clair, par exemple « QCM Git – Agossou Jean – G3 », puis Create pull request.
À retenir

Ordre à réciter : fork → clone → branche → modifier → add → commit → push → pull request. Le pull request se fait sur GitHub, pas en ligne de commande.

Chapitre 1 sur 5

Git en une image : les trois zones

Git

Un système de gestion de versions distribué : il garde l’historique de chaque modification de ton projet, et chaque copie du projet contient tout cet historique.

Imagine ton projet comme un cahier de recettes que toute la famille modifie. Sans Git, chacun écrase la version de l’autre. Avec Git, chaque changement est daté, signé et réversible.

Les trois zones à connaître par cœur

Répertoire de travailTes fichiers tels que tu les modifies(tu écris dans ton éditeur)
Zone de préparation (staging area, index)Ce qui partira dans le prochain commitgit add fichier
Dépôt local (.git)L’historique des commitsgit commit -m "message"
Dépôt distant (GitHub…)L’historique partagé avec l’équipegit push
À retenir

Le trajet d’une modification : fichier → git add → git commit → git push. Le trajet inverse : git pull (ou git fetch puis git merge).

Les branches

Branche

Une étiquette mobile qui pointe sur un commit. Travailler sur une branche, c’est faire avancer cette étiquette sans toucher aux autres.

Chapitre 4 sur 5

Fusionner et résoudre un conflit

La règle de la fusion

À retenir

On se place sur la branche qui reçoit, puis on fusionne la branche qui donne : git checkout master puis git merge fix-bogue.

Deux cas :

  • Avance rapide (fast-forward) : master n’a pas bougé depuis la création de la branche ; Git avance simplement l’étiquette.
  • Fusion à trois points : les deux branches ont avancé ; Git crée un commit de fusion.

Le conflit

Quand les deux branches ont modifié les mêmes lignes, Git s’arrête et écrit dans le fichier :

  1. Ouvre le fichier, garde la bonne version (ou un mélange), supprime les trois lignes de marqueurs.
  2. git add fichier pour dire « conflit résolu ».
  3. git commit (ou git merge --continue) pour terminer.
  4. Changé d’avis ? git merge --abort remet tout comme avant.

Fork et pull request

Le fork copie un dépôt dans ton compte GitHub. Le pull request demande au propriétaire du dépôt d’origine d’intégrer ta branche. Le premier se fait d’un clic, le second se fait sur la page GitHub après un git push.

Ne jamais réécrire l’historique partagé

reset, --amend ou rebase sur des commits déjà poussés obligent les autres à tout récupérer. Sur une branche partagée, préfère git revert.

Renommer une branche / un fichiergit branch -m a b / git mv a b
Supprimer branche / taggit branch -d nom / git tag -d v1
Corriger le dernier commitgit commit --amend -m "…"
Annuler un commit pousségit revert <hash>
Supprimer les non suivisgit clean -fd (tester avec -n)

Les pièges classiques

  • Fusion : on se place sur la branche qui reçoit.
  • switch crée avec -c, checkout crée avec -b.
  • fetch ne touche pas tes fichiers ; pull si.
