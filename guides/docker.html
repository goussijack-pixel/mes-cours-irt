Module 0 — Pourquoi Docker existe

Docker

Une plateforme qui emballe une application avec tout ce dont elle a besoin (langage, bibliothèques, configuration) dans une boîte standard, le conteneur, qui tourne à l'identique sur n'importe quelle machine.

Le problème : « ça marche chez moi »

Tu codes une API Python 3.11 avec pandas 2.1. Ton camarade a Python 3.9, le serveur de l'école a pandas 1.5, la prod tourne sous Linux et toi sous Windows. Résultat : ça plante partout sauf chez toi. Une application dépend de 5 choses qui changent d'une machine à l'autre :

  • la version du langage (Python, Node.js, Java…) ;
  • les bibliothèques et leurs versions exactes ;
  • les variables d'environnement et fichiers de configuration ;
  • les services externes (base de données, serveur web…) ;
  • le système d'exploitation et ses bibliothèques système.

Docker met ces 5 choses dans la boîte. Le conteneur est le même partout : sur ton PC, chez ton camarade, sur le serveur.

L'image qui reste

Avant les conteneurs maritimes (1956), on chargeait les bateaux sac par sac, et chaque port avait ses méthodes. Le conteneur standard a tout changé : peu importe ce qu'il y a dedans, toutes les grues, tous les camions et tous les bateaux savent le manipuler. Docker, c'est ça pour le logiciel (et c'est pour ça que son logo est une baleine qui porte des conteneurs).

Bare metal → machines virtuelles → conteneurs

ÉpoquePrincipeDéfaut
Bare metal (avant 2000)Une application = un serveur physiqueServeurs utilisés à 10-15 %, des semaines pour en installer un
Virtualisation (années 2000)Un hyperviseur découpe un serveur en plusieurs VM, chacune avec son OS completChaque VM embarque un OS entier : des Go, des minutes pour démarrer
Conteneurs (Docker, 2013)Les conteneurs partagent le noyau de l'hôte et n'isolent que l'applicationMoins isolés qu'une VM (même noyau)

Sous le capot : ce que Docker utilise de Linux

Docker n'a rien inventé de magique : il assemble trois briques du noyau Linux.

  • Les namespaces isolent ce que le conteneur voit : ses processus, son réseau, ses fichiers. Dans le conteneur, ps aux ne montre que ses propres processus.
  • Les cgroups limitent ce que le conteneur consomme : CPU et mémoire.
  • Le système de fichiers en couches (overlay2) empile des couches en lecture seule pour l'image, plus une couche d'écriture pour le conteneur.
Piège classique

Sous Windows et macOS, il n'y a pas de noyau Linux : Docker Desktop lance une petite VM Linux (via WSL 2 sous Windows) et les conteneurs tournent dedans.

À retenir

VM = une maison entière (fondations, plomberie, tout). Conteneur = un appartement dans un immeuble : il a sa porte et sa clé, mais partage les fondations (le noyau).

Chapitre 2 sur 9

Module 1 — Images, conteneurs et cycle de vie

Vérifier l'installation

Que s'est-il passé avec hello-world ?

  1. Le daemon cherche l'image en local : elle n'y est pas.
  2. Il la télécharge depuis Docker Hub (pull).
  3. Il crée un conteneur à partir de l'image.
  4. Il exécute le programme, qui affiche son message, puis le conteneur s'arrête.

Image ou conteneur ?

Image et conteneur

Une image est un modèle en lecture seule, comme une classe en POO. Un conteneur est une instance de cette image, qui tourne, comme un objet. Une image peut donner naissance à 100 conteneurs.

Les tags : toujours préciser la version

latest ne veut pas dire « la plus récente »

C'est juste le tag par défaut. Aujourd'hui latest = 1.25, demain 1.27 : ton application peut casser sans que tu aies touché à une ligne. En production, on fige toujours la version.

Le cycle de vie complet

Arrêté ≠ supprimé

Un conteneur arrêté (Exited) garde sa couche d'écriture et réapparaît avec start. Un conteneur supprimé a disparu pour toujours, avec tout ce qu'il contenait.

Les logs

Une ligne de log nginx se lit ainsi : 127.0.0.1 - [30/May/2026:10:23:45] "GET / HTTP/1.1" 200 615 "Wget" = qui, quand, quelle requête, code HTTP (200 OK, 404 introuvable, 500 erreur serveur), taille, logiciel client.

Module 2 — Aller plus loin avec docker run

Entrer dans un conteneur : -it et exec

run ou exec ?

docker run crée un nouveau conteneur. docker exec entre dans un conteneur existant. Pour déboguer un serveur en marche, c'est toujours exec.

Les images alpine n'ont pas bash

Avec nginx:1.25-alpine, utilise sh à la place de bash.

Configurer avec -e (variables d'environnement)

Pourquoi des variables plutôt qu'un fichier dans l'image ? Parce que la même image sert en développement, en test et en production : seule la configuration change, injectée au démarrage. Et les secrets ne sont jamais écrits dans l'image.

Variable de l'image MySQLRôle
MYSQL_ROOT_PASSWORDObligatoire : mot de passe du superutilisateur
MYSQL_DATABASECrée une base au premier démarrage
MYSQL_USER / MYSQL_PASSWORDCrée un utilisateur dédié

Limiter les ressources

Sans limite, un conteneur qui fuit en mémoire peut faire tomber toute la machine. Avec --memory, c'est lui seul que le noyau tue (OOM).

La leçon qui prépare le module 5 : les données sont volatiles

  1. On lance MySQL sans volume, on crée une table et on insère Alice et Bob.
  2. docker rm -f mysql-volatile supprime le conteneur.
  3. On relance un conteneur depuis la même image : la table a disparu.

Ce n'est pas un bug : les données vivaient dans la couche d'écriture du conteneur, détruite avec lui. Le module 5 apporte la solution.

Module 3 — Déboguer et inspecter

docker logs comme un pro

docker inspect : la carte d'identité complète

docker inspect renvoie un gros JSON. On en extrait une valeur avec --format et la syntaxe des gabarits Go :

docker top et docker stats

La méthode de diagnostic en 4 questions

  1. 1. Est-il vivant ? docker ps -a : Up ou Exited ?
  2. 2. Qu'a-t-il dit ? docker logs --tail 50 : le message d'erreur est presque toujours là.
  3. 3. Comment est-il mort ? docker inspect --format '{{.State.ExitCode}} {{.State.OOMKilled}}'.
  4. 4. Que se passe-t-il dedans ? docker stats, docker top, puis docker exec -it … sh.
SymptômeCause probablePreuve
S'arrête aussitôt, code 1Commande ou configuration invalidedocker logs
Code 137, OOMKilled: trueLimite mémoire trop basseinspect + --memory
Tourne mais répond malSaturation CPU/RAM ou erreur applicativestats, logs -t --since

Module 4 — Réseau et ports

Les trois drivers réseau

DriverComportementUsage
bridge (défaut)Réseau privé interne ; on publie des ports vers l'hôte95 % des cas
hostLe conteneur utilise directement le réseau de l'hôtePerformance, outils réseau (Linux)
noneAucun réseauTâches isolées, sécurité

Publier un port avec -p hôte:conteneur

Piège classique

« port is already allocated » : un autre programme utilise déjà le port de l'hôte. Change le port de gauche (-p 8081:80), jamais celui de droite.

Réseaux personnalisés et DNS interne

Sur le bridge par défaut, les conteneurs ne se trouvent que par leur adresse IP. Sur un réseau créé par toi, Docker fournit un DNS interne : chaque conteneur est joignable par son nom.

À retenir

Une application web parle à sa base par le nom du conteneur (db), jamais par une IP qui change à chaque redémarrage. C'est exactement ce que fera Compose automatiquement.

Module 5 — Volumes et persistance

Le schéma mental

Image (lecture seule, permanente) + couche R/W (temporaire, détruite avec le conteneur) = le système de fichiers que voit le conteneur. Pour garder des données, il faut les sortir de la couche R/W.

MécanismeGéré parOù sont les donnéesUsage
Bind mountToi (chemin explicite)N'importe où sur l'hôteDéveloppement, fichiers de config
Volume nomméDocker/var/lib/docker/volumes/Production, données applicatives

Le bind mount : un dossier partagé en direct

Tu édites ton code avec ton éditeur habituel, et le serveur dans le conteneur le voit immédiatement : c'est le workflow de développement avec Docker.

Les limites du bind mount

Le chemin doit exister sur l'hôte (et diffère d'une machine à l'autre), docker volume ls ne le voit pas, et des soucis de droits apparaissent si les UID diffèrent.

Le volume nommé : des données qui survivent

Comment Docker distingue les deux avec -v

Si la partie gauche commence par / ou ./ (ou ~), c'est un bind mount. Si c'est un simple nom, c'est un volume nommé, créé automatiquement s'il n'existe pas.

Gérer les volumes

Piège classique

docker volume prune et docker compose down -v détruisent les données pour toujours. Toujours vérifier avec docker volume ls avant.

La syntaxe explicite --mount

-v est plus court à taper ; --mount est plus lisible dans les scripts et la documentation.

En production…On utilise
Bases de données (MySQL, PostgreSQL, MongoDB)Volume nommé
Fichiers envoyés par les utilisateursVolume nommé
Code source en développementBind mount
Configuration, certificats TLSBind mount :ro

Module 6 — Le Dockerfile

Dockerfile

La recette d'une image : un fichier texte, lu de haut en bas, dont chaque instruction produit une couche (layer).

Les instructions essentielles

InstructionRôlePiège
FROMImage de basePréférer -slim ou -alpine
WORKDIRRépertoire courantÉviter les cd dans RUN
COPY / ADDCopier depuis le contexteUtiliser COPY ; ADD sait aussi décompresser et télécharger
RUNExécuter pendant le buildChaîner avec && dans un seul RUN
ENVVariable permanenteVisible dans docker inspect et docker history
EXPOSEDocumenter un portIl faut quand même -p au run
CMDCommande par défautRemplacée par docker run image autre-commande
ENTRYPOINTExécutable fixeLes arguments du run lui sont ajoutés
CMD contre ENTRYPOINT

Avec ENTRYPOINT ["python"] et CMD ["app.py"] :

  • docker run mon-image exécute python app.py ;
  • docker run mon-image script.py exécute python script.py (la CMD est remplacée, l'ENTRYPOINT reste).

Construire, taguer, observer

Le cache : l'ordre des instructions compte

Docker réutilise un layer si l'instruction et tout ce qui précède n'ont pas changé. Dès qu'une ligne change, tous les layers suivants sont reconstruits.

Le Dockerfile lent

COPY . . avant RUN pip install ⇒ chaque modification d'une ligne de code réinstalle toutes les dépendances (plusieurs minutes). Copie d'abord requirements.txt, installe, puis copie le code.

.dockerignore

Même principe que .gitignore : ces fichiers ne sont pas envoyés au daemon. Le build est plus rapide, et ton .env (tes secrets) ne finit pas dans l'image.

Le build multi-étapes

L'image finale ne contient ni Node.js, ni npm, ni le code source : quelques dizaines de Mo au lieu de centaines, et moins de surface d'attaque.

Module 7 — Docker Compose

Pourquoi Compose

Une vraie application, ce sont un serveur web, une base, un cache et un worker. Sans Compose : 5 commandes docker run à taper dans le bon ordre, sans oublier une option. Avec Compose : un fichier YAML versionné avec Git, et une commande.

La structure d'un docker-compose.yml

YAML : l'indentation est la syntaxe

Des espaces, jamais de tabulations, et toujours le même nombre d'espaces (2 ou 4). Une erreur d'indentation et Compose refuse le fichier.

Option docker runClé Compose
--namecontainer_name
-p 8080:80ports: ["8080:80"]
-e CLE=valenvironment
-v vol:/cheminvolumes
--networknetworks
--memory / --cpusmem_limit / cpus
--restartrestart

Les secrets dans .env (jamais dans le YAML)

Compose lit automatiquement le fichier .env du dossier et remplace chaque ${VARIABLE} du YAML.

Les commandes

Le réseau automatique et depends_on

Compose crée un réseau <dossier>_default : chaque service joint les autres par son nom (mysql -h db).

depends_on ne veut pas dire « prêt »

depends_on: [db] garantit que le conteneur db est démarré avant web, pas que MySQL accepte déjà les connexions (il lui faut 15 à 20 s). Solutions : une logique de nouvelle tentative dans l'application, ou un healthcheck combiné à condition: service_healthy.

Module 8 — Les orchestrateurs et Kubernetes

Ce que Docker seul ne fait pas

Ton application tourne avec Compose sur un seul serveur. Ce soir il tombe en panne : tout est hors ligne, rien ne redémarre ailleurs, il faut intervenir à la main.

Besoin en productionDocker seulUn orchestrateur
Panne d'un serveurTout s'arrêteRelance automatique ailleurs (self-healing)
Montée en chargedocker run à la mainScaling automatique
Mise à jourdown puis up : coupureRolling update sans interruption, rollback
Répartition du traficAucune entre hôtesLoad balancing intégré
Parc de serveursUne seule machineDes dizaines ou des centaines
Les « neuf » de la disponibilité

99,9 % de disponibilité = moins de 8 h 46 min de panne par an. 99,99 % = moins de 53 min par an. Impossible sans orchestration.

Kubernetes (K8s)

Né chez Google (héritier du système interne Borg), rendu open source en 2014 et confié à la CNCF en 2016, c'est aujourd'hui le standard. Versions managées : GKE (Google), EKS (AWS), AKS (Azure).

De Docker à Kubernetes : tout se transfère

DockerKubernetes
Image (Dockerfile)La même image, rien ne change
docker runPod (un ou plusieurs conteneurs) géré par un Deployment (le nombre de réplicas)
docker-compose.ymlManifeste YAML qui décrit l'état désiré
-p / réseauService (IP stable + load balancing), Ingress (HTTP/TLS)
Volume nomméPersistentVolume + PVC
.env / -eConfigMap (configuration) + Secret (données sensibles)
docker statskubectl top, Prometheus et Grafana

Les alternatives

  • Docker Swarm : intégré à Docker (docker swarm init, docker stack deploy) et réutilise les fichiers Compose. Simple, mais son adoption décline depuis 2020.
  • HashiCorp Nomad : orchestre conteneurs, VM et binaires, avec un seul binaire et une configuration en HCL.
  • Services managés (Cloud Run, AWS Fargate, Azure Container Instances, ECS) : tu donnes un conteneur, le cloud gère tout le reste.

Ta progression (et le lien avec ton parcours en architecture logicielle et IA)

  1. 1. Docker seul : images, conteneurs, volumes, réseaux (ce cours).
  2. 2. Docker Compose : une stack multi-conteneurs sur une machine.
  3. 3. Swarm : premier cluster de plusieurs machines.
  4. 4. Kubernetes local : minikube, k3s ou kind.
  5. 5. Kubernetes managé : GKE, EKS ou AKS, avec CI/CD et supervision.
Pourquoi c'est vital pour un futur ingénieur IA

Un modèle d'IA ne sert à rien s'il reste dans un notebook. On le met en production dans une image Docker (une API FastAPI + le modèle), on le lance avec Compose, puis on le fait monter en charge sur Kubernetes. C'est le cœur du MLOps. Savoir écrire un Dockerfile propre est l'une des compétences les plus demandées en stage.

Déboguer en 4 questions

  1. Vivant ? docker ps -a
  2. Qu'a-t-il dit ? docker logs --tail 50
  3. Comment est-il mort ? docker inspect --format '{{.State.ExitCode}} {{.State.OOMKilled}}'

Réseau et volumes

  • -p hôte:conteneur · docker network create net · --network net : joignable par son nom.
  • Bind mount : -v ./site:/usr/share/nginx/html (développement, :ro pour la config).
  • Volume nommé : -v data:/var/lib/mysql (production : survit au docker rm).
  • ⚠️ docker volume prune et docker compose down -v détruisent les données.

Dockerfile type (Python)

CMD = remplaçable · ENTRYPOINT = fixe · EXPOSE = documentation · ENV = jamais de secret.

Compose

docker compose up -d --build · ps · logs -f svc · exec svc sh · stop · down (garde les volumes) · down -v (supprime les volumes). Secrets dans .env avec ${VAR}. depends_on = démarré, pas prêt.

Docker → Kubernetes

docker run → Pod/Deployment · Compose → manifeste · -p → Service/Ingress · volume → PersistentVolume · .env → ConfigMap/Secret · kubectl get pods, apply -f, scale --replicas=5.
